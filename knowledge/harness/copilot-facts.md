# GitHub Copilot CLI – verified facts (spike for a fourth runtime)

Probes in the box on 2026-09-07 with `@github/copilot` 1.0.83 (npm `latest`; Node 22, Linux arm64),
installed into a temporary prefix, the image unchanged, signed in with a Copilot Free account.
Sources are the CLI's own `--help` and `help <topic>` output, the ACP server's answers, its logs
under `~/.copilot/logs/` and `~/.copilot/session-state/<id>/events.jsonl`, and the GitHub
documentation or changelog where quoted. The probe driver (`acp-probe.mjs`, JSON-RPC steps from a
file) lives outside the repository.

## Why Copilot is interesting

One subscription, models from every vendor: the CLI's model list carries Claude (Fable 5.1, Opus 5,
Sonnet 5, Haiku 4.5 …), GPT (6 Astra … 5 mini), Gemini 3.x Flash, Grok, Kimi and Microsoft's
MAI-Code. The official embedding paths are the CLI itself, the Copilot SDK (spawns the CLI as a
JSON-RPC server) and the CLI's ACP server mode – path 1 of `subscription-auth-rules.md`, the
harness as a process with its own login. ADR-0011 still names OpenCode as the door to Copilot;
that detour is no longer needed.

## Shape of a metor adapter (what the spike supports)

One `copilot --acp --allow-all --no-auto-update --no-remote-export --disable-builtin-mcps
--additional-mcp-config @<bot>/.copilot-mcp.json` process per bot, the Gemini adapter's protocol
loop (initialize → session/load or session/new → session/prompt, `session/update` → chat,
`session/cancel` → interrupt), `AGENTS.md` as the role file, `~/.copilot` as the volume
`metor-copilot`, setup mode `device` with `copilot login --device-code` **under a
pseudo-terminal** that answers the plaintext-storage question. Open: the model choice (see
"Models over ACP") and the built-in GitHub MCP server as an optional connector.

| Topic | Fact | Source |
|---|---|---|
| **Package** | `@github/copilot` on npm (`latest` 1.0.83, a `prerelease` tag exists). The bin `copilot` is an npm loader that installs the platform package (`@github/copilot-linux-arm64` in the box: a 160 MB native binary with an embedded Rust runtime, not a Node script). Other installers: `curl -fsSL https://gh.io/copilot-install \| bash`, Homebrew `copilot-cli`, WinGet | npm, README, probe |
| **Auto-update is on by default** | Outside CI the CLI downloads new versions by itself (`autoUpdate`, `COPILOT_AUTO_UPDATE=false` or `--no-auto-update` to stop it; CI is detected via `CI`, `BUILD_NUMBER`, `RUN_ID`, `SYSTEM_COLLECTIONURI`). The box must pin: run every process with `--no-auto-update` (or set the env var image-wide), otherwise the version drifts under the weekly runtime check | `help environment` |
| **Plans and billing** | Usage-based since 2026-06-01: every plan carries monthly AI credits, consumed by tokens at the published API rates of the model. Free $0 (limited), Pro $10 ($15 credits), Pro+ $39 ($70), Max $100 ($200), Business $19/user, Enterprise $39/user. Copilot CLI is included in every plan; organisations can switch it off by policy. `copilot help billing`: usage in AI credits ("premium requests" only on the legacy platform); `--max-ai-credits <n>` (minimum 30) is a soft cap per session; `--usage-output-file` writes the session's usage as JSON – **not allowed together with `--acp`** (`error: option '--usage-output-file <file>' cannot be used with option '--acp'`) | github.com/features/copilot/plans, GitHub blog 2026, `help billing`, `help limits`, probe |
| **Free plan in practice** | The plans page names Haiku 4.5 and GPT-5 mini; the account's session events say `availableModels: ["gpt-5.6-luna"]` – the Free account had exactly one model, and Auto chose it. The usage file of a headless run: `totalPremiumRequestCost: 1`, `currentModel: "gpt-5.6-luna"`, per-model `modelMetrics`. Enough for a spike; a real bot wants Pro or better | probe |
| **Terms** | The Product Specific Terms (March 2026) mention CLI tools only for data retention ("GitHub Copilot retains your Prompts to those tools"); no clause on programmatic use, third-party agents, seats or competing products. A fine-grained PAT permission "Copilot Requests" exists for unattended use | terms PDF, `copilot login --help` |
| **Access is a policy, not only a plan** | Before the plan was activated the login worked but every model call failed: the model list answers HTTP 403 `unauthorized: not authorized to use this Copilot feature`; headless `-p` says `Error: Access denied by policy settings … visit https://github.com/settings/copilot`, and a `session.warning` reports `Third-party MCP servers are disabled by your organization's Copilot policy. Only built-in servers are available.`; the log adds `bypass-permissions mode DISABLED by enterprise policy (fail-closed: policy could not be determined)`. So an organisation (Business/Enterprise) can switch off the CLI, **third-party MCP servers** and **allow-all** for its members – a Copilot bot in metor needs all three on (browser, routines and connectors are MCP servers; the box is the boundary). Activating Copilot Free on the account fixed all of it, no new login needed | probe, logs |
| **Sign-in** | `copilot login`: a web flow on desktops, the **OAuth device code flow in headless environments** (SSH, containers, CI; `--device-code` forces it). Output, verified: `To authenticate, visit https://github.com/login/device and enter code XXXX-XXXX`, `Waiting for authorization...`, then `Signed in successfully as <login>.` (plus an OSC 52 clipboard escape and, without a terminal, a harmless `Failed to copy to clipboard …` line). Tokens from the environment take precedence: `COPILOT_GITHUB_TOKEN`, `GH_TOKEN`, `GITHUB_TOKEN` (fine-grained PATs with "Copilot Requests", OAuth tokens of the Copilot CLI or `gh` apps; classic `ghp_` tokens are refused). `--with-token` reads one from stdin | `copilot login --help`, probe |
| **The login needs a pseudo-terminal in the box** | No keychain in the box, so after the device flow the CLI asks `System keychain unavailable. Store token in plaintext config file? (y/N)`. **Without a TTY it does not ask: `Login succeeded, but the token was not saved. Install a system keychain or rerun login and accept plaintext storage.`** – the login is lost. No flag, config key or env var pre-accepts plaintext storage (help topics and the binary's strings checked). Verified workaround: `script -q -f -e -c "copilot login --device-code" login.log < fifo` with a FIFO as stdin, `y\n` written into the FIFO once the prompt shows – then the token lands in `~/.copilot/config.json`. metor's setup runner needs this (a pty around the command, an answer to the prompt), or the user pastes a fine-grained PAT (`--with-token`) – the Gemini-style key path | probe |
| **Credentials and state on disk** | `~/.copilot/` (`COPILOT_HOME` moves it – the volume `metor-copilot` would mount there, like `.claude`, `.codex`, `.gemini`): `config.json` (JSONC with two comment lines: `// User settings belong in settings.json.` `// This file is managed automatically.` – not plain `JSON.parse`) holds `firstLaunchAt`, `authTokens: {"https://github.com:<login>": {token}}`, `lastLoggedInUser`, `loggedInUsers`; `session-store.db` (SQLite + WAL), `session-state/<sessionId>/` (`events.jsonl`, `workspace.yaml` with cwd/name/client_name, `checkpoints/`, `files/`), `installed-plugins/`, `logs/` (`--log-dir`, `--log-level`) | probe, `help environment` |
| **Login is not done over ACP** | `initialize` answers `authMethods: [{id:"copilot-login", name:"Log in with Copilot CLI", description:"Run \`copilot login\` in the terminal", _meta:{"terminal-auth":{command:"…/copilot", args:["login"], label:"Copilot Login"}}}]` – the agent points the client at the CLI's own login. `session/new` before a login: `{"code":-32000,"message":"Authentication required"}` | probe |
| **ACP handshake** | `copilot --acp` speaks JSON-RPC 2.0 newline-delimited over stdio (`--port <n>` for TCP is documented but not in `--help`). `initialize {protocolVersion:1, clientCapabilities:{fs:{readTextFile:false, writeTextFile:false}}}` → `{protocolVersion:1, agentCapabilities:{loadSession:true, mcpCapabilities:{http:true, sse:true}, promptCapabilities:{image:true, audio:false, embeddedContext:true}, sessionCapabilities:{close:{}, list:{}}}, agentInfo:{name:"Copilot", version:"1.0.83"}, authMethods:[…]}`. ACP is a public preview since 2026-01-28 | probe, GitHub changelog |
| **session/new** | `{cwd, mcpServers:[]}` → in about 1.6–2 s `{sessionId, modes:{availableModes:[agent "Default agent mode", plan, autopilot "enables allow-all and runs until task completion (experimental)"], currentModeId:"…#agent"}, configOptions:[{id:"mode", type:"select", …}, {id:"allow_all", type:"select", currentValue:"on"/"off" (mirrors `--allow-all` on the process), options:[on, off], category:"permissions"}]}`. Mode ids are URLs `https://agentclientprotocol.com/protocol/session-modes#agent`. **No `models` key** – unlike Gemini, the answer does not list models. The CLI titles the session after the first prompt (`workspace.yaml name`, `session_info_update`) | probe |
| **Turn shapes (verified)** | `session/prompt {sessionId, prompt:[{type:"text", text}]}` → `{stopReason:"end_turn", usage:{inputTokens, outputTokens, totalTokens, thoughtTokens, cachedReadTokens, cachedWriteTokens}}`. Notifications `session/update`: `agent_thought_chunk` (reasoning, many, hidden), `agent_message_chunk {content:{type:"text", text}}` (the answer, streamed word by word), `tool_call {toolCallId:"call_…", title:"Print kernel information", kind:"execute", status:"pending", rawInput:{command:"uname -a", description}}`, `tool_call_update {toolCallId, content:[{type:"content", content:{type:"text", text:"…output…"}}]}` while the shell runs (repeated, cumulative output) and finally `{status:"completed", content:[…"<shellId: 0 completed with exit code 0>"], rawOutput:{content, detailedContent}}` – the shell output **is** in the update (Gemini's is not); `usage_update {used, size}` (context-window tokens: `size` 128000 or 200000 by model); `session_info_update {title, updatedAt}`; `config_option_update {configOptions}`; `available_commands_update` (the slash commands: add-dir, allow-all, permissions, autopilot, …). A shell task end to end: about 11 s; a plain answer: 2–4 s | probe |
| **A failed turn is not a JSON-RPC error** | The denied account's `session/prompt` answered `{stopReason:"end_turn"}` after streaming `Error: Authorization error. Your credentials may be expired or invalid. (Request ID: …)` as an ordinary `agent_message_chunk`. The adapter cannot rely on `error` to notice a broken login; the text reaches the chat as the bot's answer, which is at least visible | probe |
| **Cancel** | `session/cancel {sessionId}` during a running shell command: the prompt result came 30 ms later with **`stopReason:"end_turn"`** (not `cancelled`), the running loop (`for … sleep 0.2`) was killed – no leftover processes. The adapter treats the result after a cancel as a normal end of turn | probe |
| **Resume works** | New process: `session/list {}` → `{sessions:[{sessionId, cwd, title, updatedAt}, …]}` (all sessions of the home directory); `session/load {sessionId, cwd, mcpServers:[]}` replays the history as `session/update` (`user_message_chunk`, `tool_call`, `tool_call_update`, `agent_message_chunk`), then answers `{modes, configOptions}` (about 2 s); the next prompt knew the first command of the old session. `session/close {sessionId}` → `{}` | probe |
| **Permissions in ACP** | `--allow-all` (= `--allow-all-tools --allow-all-paths --allow-all-urls`, alias `--yolo`, env `COPILOT_ALLOW_ALL=true`) on the process: the box is the boundary (ADR-0004); the session's `configOptions.allow_all` shows `on`. **Without it** the agent asks: `session/request_permission {sessionId, toolCall:{toolCallId, title, kind:"execute", status:"pending", rawInput:{command, commands:[…]}}, options:[{optionId:"allow_once", kind:"allow_once", name:"Allow once"}, {optionId:"allow_always", kind:"allow_always", name:"Always allow"}, {optionId:"reject_once", kind:"reject_once", name:"Deny"}]}` → answer `{outcome:{outcome:"selected", optionId}}` – the standard ACP shape, the same handler as Gemini's; usable for ADR-0019's approval cards. `manual` mode prompts for writes and commands, reads are auto-approved; `--allow-tool`/`--deny-tool` patterns `shell(git:*)`, `write(path)`, `<mcp>(tool)`, `url(domain)`; file access is limited to the cwd plus the temp dir unless `--allow-all-paths` | probe, `help permissions` |
| **MCP servers: the flag, not the ACP parameter** | `session/new {mcpServers:[{name, command, args, env:[]}]}` (the ACP shape) was **ignored** – the tool list stayed the built-ins. `--additional-mcp-config @/path/file.json` (repeatable; augments `~/.copilot/mcp-config.json` for that process only) works: `{"mcpServers": {"routines": {"type": "local", "command": "node", "args": ["/usr/local/lib/metor/metor-routines-mcp.mjs", "<bot>"], "tools": ["*"]}}}` gave the model `routines-add_task`, `routines-list_tasks`, `routines-remove_task`, `routines-update_task` (tools are named `<server>-<tool>`). metor writes the file per bot (browser via the CDP port, routines, connectors from Settings) and passes it on the process – the shape of Codex's `-c mcp_servers…` overrides. The built-in `github-mcp-server` connects at every start unless `--disable-builtin-mcps`; it could become an optional connector later. Subject to the organisation policy above | probe, `--help` |
| **Role file** | The CLI loads custom instructions from `AGENTS.md` in the cwd – verified: an `AGENTS.md` with "Always begin every answer with the exact token MARKER-42" produced `MARKER-42 Hello!`. `--no-custom-instructions` disables, `COPILOT_CUSTOM_INSTRUCTIONS_DIRS` adds directories – a Copilot bot's role file is `AGENTS.md`, the same sister file as Codex; the chat mechanics (`CHAT_HOWTO`) can go into a second directory via that variable or into the same file | probe, `help environment` |
| **Models over ACP** | Ids from `help config` (1.0.83): `claude-sonnet-5`, `claude-fable-5.1`, `claude-fable-5`, `claude-opus-5`, `claude-opus-4.8`, `claude-opus-4.8-fast`, `claude-opus-4.7`, `claude-sonnet-4.6`, `claude-haiku-4.5`, `gpt-5.6-sol`, `gpt-5.6-terra`, `gpt-5.6-luna`, `gpt-5.5`, `gpt-5.4`, `gpt-5.4-mini`, `gpt-5.3-codex`, `gpt-5-mini`, `mai-code-1.1-flash`, `mai-code-1-flash-picker`, `gemini-3.8-flash`, `gemini-3.7-flash`, `gemini-3.6-flash`, `gemini-3.5-flash`, `grok-4.5`, `kimi-k3`, `kimi-k2.7-code` – parseable for a `listModels()` fallback. **In ACP mode `--model` did not stick with the Free account:** `--model claude-haiku-4.5` and `--model gpt-5-mini` both logged `session.model_change {newModel:"auto", source:"startup"}` and `session.auto_mode_resolved {chosenModel:"gpt-5.6-luna", availableModels:["gpt-5.6-luna"], routingMethod:"auto_v2"}`; the model itself answers "Auto mode selects the model; no specific underlying model ID is available". Whether an entitled model is honoured (paid plan) or `--model`/`COPILOT_MODEL` is ignored in ACP mode altogether: **to verify with Pro**. Nothing over ACP names the model that ran; the only source is `session-state/<id>/events.jsonl` (`session.auto_mode_resolved.chosenModel`, `assistant.message.model`) – readable for the label, but the CLI's private format. `--effort none…max`, `--context long_context` (tiered pricing) exist as flags | `help config`, probe |
| **Side models** | The auto session's events also show `gpt-5.4-nano` (28 events) next to the main model – the CLI's helper model for titles, sentiment and similar bookkeeping; not the answer's model | events.jsonl |
| **Headless JSON** | `copilot -p "…" --allow-all --output-format json` prints JSONL events: `session.warning {message, warningType:"policy"}`, `session.mcp_server_status_changed {serverName, status:pending→connected}`, … ; `-s` prints only the answer.
