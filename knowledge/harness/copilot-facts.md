# GitHub Copilot CLI – verified facts (spike for a fourth runtime)

Probes in the box on 2026-09-07 with `@github/copilot` 1.0.83 (npm `latest`; Node 22, Linux arm64),
installed into a temporary prefix, the image unchanged. Sources are the CLI's own `--help` and
`help <topic>` output, the ACP server's answers, its logs under `~/.copilot/logs/`, and the GitHub
documentation or changelog where quoted. Status: **spike in progress** – rows marked "to verify"
are documented claims the probe has not reached yet (the spike account was denied the CLI by
policy, see "Access is a policy").

## Why Copilot is interesting

One subscription, models from every vendor: the CLI's model list carries Claude (Fable 5.1, Opus 5,
Sonnet 5, Haiku 4.5 …), GPT (6 Astra … 5 mini), Gemini 3.x Flash, Grok, Kimi and Microsoft's
MAI-Code. The official embedding paths are the CLI itself, the Copilot SDK (spawns the CLI as a
JSON-RPC server) and the CLI's ACP server mode – path 1 of `subscription-auth-rules.md`, the
harness as a process with its own login. ADR-0011 still names OpenCode as the door to Copilot;
that detour is no longer needed.

|---|---|---|
| **Package** | `@github/copilot` on npm (`latest` 1.0.83, a `prerelease` tag exists). The bin `copilot` is an npm loader that installs the platform package (`@github/copilot-linux-arm64` in the box: a 160 MB native binary with an embedded Rust runtime, not a Node script). Other installers: `curl -fsSL https://gh.io/copilot-install \| bash`, Homebrew `copilot-cli`, WinGet | npm, README, probe |
| **Auto-update is on by default** | Outside CI the CLI downloads new versions by itself (`autoUpdate`, `COPILOT_AUTO_UPDATE=false` or `--no-auto-update` to stop it; CI is detected via `CI`, `BUILD_NUMBER`, `RUN_ID`, `SYSTEM_COLLECTIONURI`). The box must pin: run every process with `--no-auto-update` (or set the env var image-wide), otherwise the version drifts under the weekly runtime check | `help environment` |
| **Plans and billing** | Usage-based since 2026-06-01: every plan carries monthly AI credits, consumed by tokens at the published API rates of the model. Free $0 (limited, Haiku 4.5 and GPT-5 mini), Pro $10 ($15 credits), Pro+ $39 ($70), Max $100 ($200), Business $19/user, Enterprise $39/user; all plans see the same models. Copilot CLI is included in every plan; organisations can switch it off by policy. `copilot help billing`: usage in AI credits ("premium requests" only on the legacy platform); `--max-ai-credits <n>` (minimum 30) is a soft cap per session; `--usage-output-file` writes the session's usage as JSON | github.com/features/copilot/plans, GitHub blog 2026, `help billing`, `help limits` |
| **Terms** | The Product Specific Terms (March 2026) mention CLI tools only for data retention ("GitHub Copilot retains your Prompts to those tools"); no clause on programmatic use, third-party agents, seats or competing products. A fine-grained PAT permission "Copilot Requests" exists for unattended use | terms PDF, `copilot login --help` |
| **Access is a policy, not only a plan** | Signed in, but every model call of the spike account fails: the model list answers HTTP 403 `unauthorized: not authorized to use this Copilot feature`; headless `-p` says `Error: Access denied by policy settings … Your Copilot CLI policy setting may be preventing access … visit https://github.com/settings/copilot`, and a `session.warning` reports `Third-party MCP servers are disabled by your organization's Copilot policy. Only built-in servers are available.` So an organisation (Business/Enterprise) can switch off the CLI **and third-party MCP servers** for its members – a Copilot bot in metor needs both policies on (browser, routines and connectors are MCP servers). The log also notes `[managedSettings] … no bypass restriction in force (managed policy absent)`: a managed policy can forbid `--allow-all` (changelog 1.0.57 "Enforce bypass permissions policy") – then the box-is-the-boundary model does not work for that account | probe, logs, changelog |
| **Sign-in** | `copilot login`: a web flow on desktops, the **OAuth device code flow in headless environments** (SSH, containers, CI; `--device-code` forces it). Output, verified: `To authenticate, visit https://github.com/login/device and enter code XXXX-XXXX`, `Waiting for authorization...`, then `Signed in successfully as <login>.` (plus an OSC 52 clipboard escape and, without a terminal, a harmless `Failed to copy to clipboard …` line). Tokens from the environment take precedence: `COPILOT_GITHUB_TOKEN`, `GH_TOKEN`, `GITHUB_TOKEN` (fine-grained PATs with "Copilot Requests", OAuth tokens of the Copilot CLI or `gh` apps; classic `ghp_` tokens are refused). `--with-token` reads one from stdin | `copilot login --help`, probe |
| **The login needs a pseudo-terminal in the box** | No keychain in the box, so after the device flow the CLI asks `System keychain unavailable. Store token in plaintext config file? (y/N)`. **Without a TTY it does not ask: `Login succeeded, but the token was not saved. Install a system keychain or rerun login and accept plaintext storage.`** – the login is lost. No flag, config key or env var pre-accepts plaintext storage (help topics and the binary's strings checked). Verified workaround: `script -q -f -e -c "copilot login --device-code" login.log < fifo` with a FIFO as stdin, `y\n` written into the FIFO once the prompt shows – then the token lands in `~/.copilot/config.json`. metor's setup runner needs this (a pty around the command, an answer to the prompt), or the user pastes a fine-grained PAT (`--with-token`) – the Gemini-style key path | probe |
| **Credentials and state on disk** | `~/.copilot/` (`COPILOT_HOME` moves it – the volume `metor-copilot` would mount there, like `.claude`, `.codex`, `.gemini`): `config.json` (JSONC with two comment lines: `// User settings belong in settings.json.` `// This file is managed automatically.` – not plain `JSON.parse`) holds `firstLaunchAt`, `authTokens: {"https://github.com:<login>": {token}}`, `lastLoggedInUser`, `loggedInUsers`; `session-store.db` (SQLite + WAL), `session-state/<sessionId>/`, `installed-plugins/`, `logs/` (`--log-dir`, `--log-level`) | probe, `help environment` |
| **Login is not done over ACP** | `initialize` answers `authMethods: [{id:"copilot-login", name:"Log in with Copilot CLI", description:"Run \`copilot login\` in the terminal", _meta:{"terminal-auth":{command:"…/copilot", args:["login"], label:"Copilot Login"}}}]` – the agent points the client at the CLI's own login. `session/new` before a login: `{"code":-32000,"message":"Authentication required"}` | probe |
| **ACP handshake** | `copilot --acp` speaks JSON-RPC 2.0 newline-delimited over stdio (`--port <n>` for TCP is documented but not in `--help`). `initialize {protocolVersion:1, clientCapabilities:{fs:{readTextFile:false, writeTextFile:false}}}` → `{protocolVersion:1, agentCapabilities:{loadSession:true, mcpCapabilities:{http:true, sse:true}, promptCapabilities:{image:true, audio:false, embeddedContext:true}, sessionCapabilities:{close:{}, list:{}}}, agentInfo:{name:"Copilot", version:"1.0.83"}, authMethods:[…]}`. ACP is a public preview since 2026-01-28 | probe, GitHub changelog |
| **session/new** | `{cwd, mcpServers:[]}` → in about 2 s `{sessionId, modes:{availableModes:[agent "Default agent mode", plan, autopilot "enables allow-all and runs until task completion (experimental)"], currentModeId:"…#agent"}, configOptions:[{id:"mode", type:"select", …}, {id:"allow_all", type:"select", currentValue:"on" (with `--allow-all` on the process), options:[on, off], category:"permissions"}]}`. Mode ids are URLs `https://agentclientprotocol.com/protocol/session-modes#agent`. No `models` key in the answer of the denied account – the log says `Failed to retrieve models for ACP session` (403), so with access the answer probably lists them like Gemini's: to verify | probe, logs |
| **Notifications seen** | `session/update` with `available_commands_update` (the slash commands: add-dir, allow-all, permissions, autopilot, …), `session_info_update {title, updatedAt}` (the CLI titles the session after the first prompt), `usage_update {used:10493, size:128000}` (context-window tokens – the 128k window of the default model; not credits), `agent_message_chunk {content:{type:"text", text}}` | probe |
| **A failed turn is not a JSON-RPC error** | The denied account's `session/prompt` answered `{stopReason:"end_turn"}` after streaming `Error: Authorization error. Your credentials may be expired or invalid. (Request ID: …)` as an ordinary `agent_message_chunk`. The adapter cannot rely on `error` to notice a broken login; the text reaches the chat as the bot's answer, which is at least visible | probe |
| **Headless JSON** | `copilot -p "…" --allow-all --output-format json` prints JSONL events: `session.warning {message, warningType:"policy"}`, `session.mcp_server_status_changed {serverName:"github-mcp-server", status:pending→connected}` – the built-in GitHub MCP server connects at every start (`--disable-builtin-mcps` switches it off) | probe |
| **Permissions in ACP** | `--allow-all` (= `--allow-all-tools --allow-all-paths --allow-all-urls`, alias `--yolo`, env `COPILOT_ALLOW_ALL=true`) on the process: the box is the boundary (ADR-0004). The session's `configOptions` show `allow_all` and it can be toggled per session (CLI 1.0.39+). Without it: `manual` mode prompts for writes and commands, reads are auto-approved; `--allow-tool`/`--deny-tool` patterns `shell(git:*)`, `write(path)`, `<mcp>(tool)`, `url(domain)`; file access is limited to the cwd plus the temp dir unless `--allow-all-paths` | `help permissions`, probe, changelog |
| **MCP servers** | Global `~/.copilot/mcp-config.json`; per process `--additional-mcp-config <json or @file>` (repeatable) augments it for that session only – metor's per-bot servers (browser via the CDP port, routines, connectors) go there, the same shape as Codex's `-c mcp_servers…` overrides. Shape of the JSON: to verify. Subject to the organisation policy above | `--help`, probe |
