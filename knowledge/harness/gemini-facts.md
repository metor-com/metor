# Gemini CLI – verified facts (third runtime, ADR-0016)

Probes in the box on 2026-09-05 with `@google/gemini-cli` 0.58.0 (Node 22). Sources are the
CLI's own `--help`, its output, and the documentation at geminicli.com where quoted.

| Topic | Fact | Source |
|---|---|---|
| **Sign-in methods** | Google account ("Sign in with Google", Gemini Code Assist for individuals: free tier "60 requests/min and 1,000 requests/day", Google AI Pro/Ultra raise the limits), Gemini API key (`GEMINI_API_KEY`, free tier "1000 requests/day"), Vertex AI. Headless mode without cached credentials fails with exit code 41 and lists the env vars `GEMINI_API_KEY`, `GOOGLE_GENAI_USE_VERTEXAI`, `GOOGLE_GENAI_USE_GCA` | docs, probe |
| **Google account login: closed for the CLI (2026-09-05)** | Over ACP, `authenticate {methodId:"oauth-personal"}` answers `{"error":{"code":-32000,"message":"This client is no longer supported for Gemini Code Assist for individuals. To continue using Gemini, please migrate to the Antigravity suite of products: https://antigravity.google"}}` – in the morning the link still came, by noon the server refused. metor therefore signs Gemini in with an API key | probe |
| **API key path** | Headless `-p` reads `GEMINI_API_KEY` from `~/.gemini/.env` (a bogus key reaches the API: "Error generating content via API"). Over ACP the key must be in the process environment: `authenticate {methodId:"gemini-api-key"}` → `{}`, `session/new {cwd, mcpServers:[]}` → `{sessionId, modes:{availableModes:[default, autoEdit, yolo, …]}}`, a `session/update` with `available_commands_update`, `session/prompt` → with a bogus key a 400 "API key not valid" | probe |
| **Google login was a code flow like Claude's** | With `NO_BROWSER=true` the CLI prints `Please visit the following URL to authorize the application:` + `https://accounts.google.com/o/oauth2/v2/auth?redirect_uri=https%3A%2F%2Fcodeassist.google.com%2Fauthcode&…` and then `Enter the authorization code:` and reads one line from stdin. The redirect goes to a Google page that shows the code – no localhost callback, no relay | probe |
| **The login runs over ACP, no terminal needed** | `gemini --acp` speaks JSON-RPC 2.0 over stdio. `initialize` answers with `authMethods` (`oauth-personal` "Log in with Google", `gemini-api-key`, `vertex-ai`, `gateway`) and `agentCapabilities: { loadSession: true, promptCapabilities: { image, audio, embeddedContext }, mcpCapabilities: { http, sse } }`. `authenticate {methodId:"oauth-personal"}` under `NO_BROWSER=true` prints the URL and code prompt above on stdout and answers the request once the code is in – metor's setup assistant uses exactly this (registry `setup.stdin` + `done` pattern) | probe |
| **The interactive TUI needs a real terminal** | Plain `gemini` under `script` (pseudo-terminal) shows the auth-method dialog and prints the same URL after Enter, but needs keystrokes; headless `-p` without credentials: "Manual authorization is required but the current session is non-interactive" | probe |
| **Headless turns** | `-p "…"` with `--output-format json` or `stream-json` (events `init`, `message`, `tool_use`, `tool_result`, `error`, `result`); `--approval-mode default|auto_edit|yolo|plan`; `--skip-trust` or `GEMINI_CLI_TRUST_WORKSPACE=true` (otherwise the trusted-folders gate refuses); `-m` model; `--resume latest|<index>`, `--list-sessions`, `--session-id <uuid>`, `--session-file`. Sessions are saved automatically per project directory under `~/.gemini/tmp/<project_hash>/` | `--help`, docs |
| **Not used: `-p` per turn** | metor keeps one `gemini --acp` process per bot instead (session/new, session/load for resume, session/prompt), the same shape as the Codex adapter; `--approval-mode yolo --skip-trust -m <model>` on that process | design |
| **MCP servers** | Project settings `.gemini/settings.json` in the cwd: `mcpServers.<name>` with `command`/`args`/`env`/`cwd`/`timeout`/`trust` (stdio), `url` (SSE) or `httpUrl` (streamable HTTP) with `headers`. Verified: the CLI started metor's routines server from such a file and reported it "Connected" (`gemini mcp list`); `gemini mcp add|remove|list|enable|disable` exist | probe, docs |
| **Context files** | `GEMINI.md` in the project (the bot's role file) and `~/.gemini/GEMINI.md` (global – metor writes the chat mechanics there, see the adapter) | docs |
| **Credentials on disk** | The runtime's home `~/.gemini/` (settings, `oauth_creds.json` after a Google login, `.env` for `GEMINI_API_KEY`, `tmp/` sessions) – a volume `metor-gemini` in metor, like `.claude` and `.codex` | docs, design |
| **Models over ACP** | `session/new` answers `{sessionId, modes:{availableModes:[default, autoEdit, yolo, …]}, models:{availableModels:[{modelId:"auto", name:"Auto", description:"Let Gemini CLI decide the best model for the task: gemini-3.1-pro-preview, gemini-3.5-flash"}, {modelId:"gemini-3.1-pro-preview-customtools", name:"gemini-3.1-pro-preview"}, {modelId:"gemini-3-flash-preview…"}, …]}}`. The prompt result carries `_meta.quota.model_usage: [{model:"gemini-3.5-flash", token_count:{input_tokens, output_tokens}}, …]` – the model that actually answered. metor lists the models from `session/new` (with the key) and labels "Auto" with the last model used | probe with a working key, 2026-09-05 |
| **Turn shapes (verified with a working key)** | `session/prompt` → `{stopReason:"end_turn", _meta:{quota:…}}`. Notifications `session/update`: `agent_thought_chunk {content:{type:"text",text}}` (reasoning, hidden), `agent_message_chunk {content:{type:"text",text}}` (the answer, streamed), `tool_call {toolCallId, status:"in_progress", title:"echo shapes-test", content:[{type:"content", content:{type:"text", text:"[current working directory …] (…)"}}], locations:[], kind:"execute"}`, `tool_call_update {toolCallId, status:"completed", title, content:[…] or [], locations, kind}` – the shell's output is not in the update. Internal bookkeeping calls come as `tool_call` with `kind:"think"` and titles like "Update tactical intent: …" (hidden). `available_commands_update` lists the slash commands | probe |
| **Resume works** | A bot's host restarted with its stored session id: `session/load {sessionId, cwd, mcpServers:[]}` succeeded and the bot answered "I ran the command `uname -a`, which reported: Linux metor-box 6.18.35 …" about the previous turn. A load right after `session/new` in the same process fails with "No previous sessions found for this project" – sessions are persisted later | probe, live bot |
| **Timing** | A shell task with the answer: about 10 s end to end; the model list over ACP under 2 s | live bot |
